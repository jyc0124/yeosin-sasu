# PRD — 여신 창구 코파일럿 (가칭, 영문 LoanDesk Copilot)

> v1.0 · 2026-11-13 · Liner .EXE-THON 출품작
> 관련 문서: `data/factsheet.md`(정책 사실 기준), `data/testset_v0.md`(평가셋), `data/liner_spike/REPORT.md`(Liner 검증), `docs/PLAN.md`(개발 계획)

---

## 1. 한 줄 정의

**은행 지점 창구 직원이 자주 묻던 대출 규정 질문을 입력하면, 근거가 붙은 판정 카드를 30초 안에 돌려주는 에이전트입니다. 정책이 바뀌면 그 사실을 먼저 찾아내 기존 답변을 갱신합니다.**

## 2. 문제 정의

### 2.1 무슨 일이 벌어지고 있나
- 2025.6.27부터 2026.8.13까지 대출 대책이 **1년 남짓 동안 5차례** 나왔습니다(6.27, 9.7, 10.15, 4.1, 8.13). 대책마다 **발표일, 시행일, 경과조치, 예외 8가지 이상**이 서로 다릅니다.
- 8.13 대책은 핵심 예외 판단을 **"금융회사 여신심사위원회"에 맡겼고**, 금융위는 일률적인 가이드라인 대신 **"유권해석으로 보완"**하겠다고 밝혔습니다. 해석 부담이 은행으로 내려왔고, 언론은 이를 "창구 혼선", "대출책임 떠넘기기 논란"으로 보도했습니다.
- **실제 집행 기준인 경과조치는 보도자료나 FAQ가 아니라 2주 뒤 별도 사이트에 게시된 행정지도(8.28)에** 들어 있습니다. 창구 직원이 혼자 찾아내기 어려운 구조입니다.

### 2.2 누가, 얼마나 불편한가
- **누가**: 시중은행 지점에서 주담대·전세대출을 상담하는 창구 직원
- **언제**: 대책이 발표된 직후부터 시행 직전까지. 지금은 비거주 1주택자 규제(2027.1.1 시행)를 앞둔 시점입니다.
- **규모(공식 수치)**
  - 수도권·규제지역 APT를 보유한 1주택자의 전세대출 **약 9.3조 원(6.0만 건)**이 8.13 규제 영향권입니다.
  - 다주택자 주담대 중 2026년 만기 도래분이 **약 1.2만 건**입니다(4.17~6월에만 2,001건 상환).
- **현장 관찰**: 지점 직원 커뮤니티에서 같은 유형의 해석 질문이 반복됩니다. 답이 공식 근거인지 개인 경험인지 구분할 수 없고, 본점 회신을 기다리는 사이 고객 일정이 밀립니다.
  - **현행 해결 소요시간(설문에 답한 현직 지점 직원 1명, 2026-11-17)**: 짧으면 수 분~30분, 간혹 2~3일. 오래 걸리는 경우는 ① 공지된 지침만으로 해결하기 어려워 **본점 직원 확인**이 필요할 때(이런 경우가 꽤 있음), ② 가장 오래 걸리는 것은 본점 직원이 다시 **외부기관(HUG, 국토부 등)에 지침을 문의**할 때 — 외부기관 문의 게시판에 글을 올리는 방식이라 더 늦어진다.
  - 측정치가 아니라 1명의 전언입니다(설문 예시에 "본점 회신까지 2~3일"이 있었음). 기획서에는 "현직 지점 직원 응답 기준, 짧으면 수 분, 본점·외부기관을 거치면 2~3일"로만 쓰고 평균처럼 표현하지 않습니다. 도구 쪽 수치(판정 카드 10초 이내)와 나란히 둡니다.
  - 시사점: 지연은 지점 → 본점 → 외부기관으로 **질문이 위로 넘어갈 때마다** 커진다. 코파일럿이 줄이는 것은 (a) 공지된 원문으로 답이 나오는 질문을 지점에서 끝내는 것, (b) 넘겨야 하는 질문을 근거·쟁점이 정리된 질의서로 한 번에 넘기는 것, (c) 한 번 받은 본점 해석을 FAQ로 재사용해 같은 질문이 다시 올라가지 않게 하는 것.

### 2.3 진짜 병목
규정을 **찾는 것**보다 **이 고객 사례에 어느 규정을, 어느 시점 기준으로, 어떤 예외와 함께 적용하는지** 판단하는 것이 어렵습니다. 그리고 **지점이 판단할 수 없는 것**(여신심사위 사항)을 빠르게 가려내 본점에 넘기는 것도 병목입니다.

## 4. 범위

### 포함 (MVP)
- **정책 모듈 2개**
  - **M1**: 8.13 비거주 1주택자 전세대출 제한(경과조치 포함)
  - **M2**: 4.1 다주택자 수도권·규제지역 APT 주담대 만기연장 제한
- **기능**: F1 판정 카드, F2 정책 변경 감시, F3 본점 질의와 FAQ(경량), F4 평가 하네스
- **데이터**: 금융위 공개 원문 + **가상 A은행 내부 지침**(여신심사위 기준, 임대사업자 판단 기준 등)

### 제외
- 실제 대출 승인이나 한도 계산(LTV·DSR 수치 계산은 제외하고 규정 안내만 함)
- 실제 고객정보와 은행 내부자료 사용, 은행 전산 연동, 로그인과 권한 관리
- 다른 대책(6.27·10.15 한도 등)의 세부 판정. 배경 지식으로만 둡니다.

## 5. 기능 요구사항

### F1. 판정 카드 (핵심)
**입력**: 창구 말투의 자유 질문. 예: "다주택 고객 12월 만기, 세입자 있음, 연장 돼요?"

| 단계 | 처리 | 담당 |
|---|---|---|
| 1. 조건 추출 | 질문을 구조화된 사례로 바꿈(차주 유형, 주택 수, 소재지, 주택 유형, 대출 종류, 만기일, 임대차 정보 등) | Liner Router (`json_schema`) |
| 2. 모듈 선택 | M1인지 M2인지, 범위 밖인지 분류 | Liner Router (`routing_strategy: cost`) |
| 3. 누락 확인 | 판정에 꼭 필요한 값이 비어 있으면 **역질문**을 생성하고 멈춤 | 규칙 엔진 |
| 4. 판정 | 날짜·조건 규칙으로 판정 코드 산출 | **규칙 엔진(코드)**. LLM은 판정하지 않음 |
| 5. 근거 첨부 | 판정에 쓴 Fact ID에 해당하는 원문 문장과 출처 링크 | 원문 저장소 |
| 6. 서류와 다음 행동 | 징구 서류, 고객 안내 문구, 본점 질의 필요 여부 | 규칙 엔진 + 템플릿 |
| 7. 설명 | 사람이 읽기 쉬운 설명. **원문 대조를 통과한 문장만 표시** | Liner Router (`quality`) + 검증기 |

**출력: 판정 카드**
- 판정 배지: 허용, 조건부, 불허, 심사위, 보류, 역질문, 내부지침 중 하나
- 적용 규정과 기준일. 예: "8.28 행정지도 경과조치, 만기 12/20 → 종전 규정"
- 체크리스트: 확인한 조건과 미확인 조건
- 필요 서류 목록
- 근거 원문 인용(조항 단위)과 공식 링크
- 본점 질의서 초안(심사위·보류인 경우)
- 지식 버전 표시. 예: "KB v2 · 2026-08-28 행정지도 반영"

**수용 기준**
- 테스트셋에서 판정 코드 일치율 **90% 이상**
- C유형(함정) 문항에서 단정하지 않고 보류·역질문으로 답하는 비율 **100%**
- 인용한 근거가 판정을 실제로 뒷받침하는 비율 **95% 이상**
- 카드 첫 결과(판정 배지)를 **10초 이내**에 표시

### F2. 정책 변경 감시 (Liner 핵심 장면)
1. **감시 질의 세트**를 실행합니다(공식 문서명, 기관명, 주제 키워드 조합). 대상은 Liner Search API와 MCP `search_legal`입니다.
2. **출처 신뢰도 필터**를 적용합니다.
   - 1등급: fsc.go.kr, better.fsc.go.kr, korea.kr, fss.or.kr, law.go.kr
   - 2등급: 주요 언론
   - 제외: SNS·블로그
3. **새 문서를 판정**합니다. 알려진 문서 목록에 없는 1등급 문서만 남깁니다.
4. **원문을 확보**합니다. PDF·HWP를 받아 텍스트로 추출합니다.
5. **조항을 구조화**합니다. Router가 원문에서 적용 대상, 예외, 시행일, 경과조치를 추출해 Fact 후보로 만듭니다.
6. **차이를 분석**합니다. 기존 Fact Sheet와 비교해 신규·변경 Fact를 찾고, **영향받는 규칙과 FAQ, 테스트 문항**을 표시합니다.
7. **사람이 승인**하면 지식 버전을 올리고(KB v1 → v2), 영향받은 판정 카드를 다시 계산합니다.

**데모 시나리오(타임머신)**
- KB v1은 8.13 보도자료와 FAQ만 반영한 상태입니다. 이때 B02를 판정하면 "보류"가 나옵니다.
- 감시를 실행하면 8.28 행정지도를 발견하고, 경과조치 Fact 2개를 추가하자는 변경 제안이 나옵니다.
- 승인하면 KB v2가 되고, B02 판정이 "조건부(종전 규정, 증액 시 신규 규정)"로 바뀝니다.

**수용 기준**: 데모 시점에 실제 Liner 호출로 8.28 행정지도를 1등급 후보로 잡아내고, 경과조치 2개 항목을 추출합니다.

### F3. 본점 질의와 FAQ (경량)
- 판정이 "심사위"나 "보류"면 본점 질의서를 자동 작성합니다. 사례 요약, 확인한 규정, 쟁점, 필요 판단, 첨부 근거가 들어갑니다.
- 본점 역할 화면에서 답변을 입력하고 **승인**하면 FAQ로 등록됩니다(승인일, 적용 KB 버전, 근거 포함).
- 새 질문이 승인된 FAQ와 비슷하면 판정 카드에 "승인된 본점 해석 있음"을 표시합니다.
- **외부기관 문의 단계**(현장 관찰: 가장 오래 걸리는 단계, 2.2): 본점도 원문으로 답할 수 없는 쟁점이면 코드가 문의처를 가릅니다(`lib/hq/external.ts`, LLM 없음). 원문 공백 G-01~G-04는 금융위원회(+8.13 전세 쟁점은 전세대출 보증기관), G-07은 국토교통부, G-08은 행정안전부입니다. 정책이 금융회사에 맡긴 G-05·G-06과 심사위·내부지침 판정은 "외부 문의 불필요"로 표시해 쓸데없는 문의를 막습니다.
  - 고객 정보 없이 쟁점·원문 조항만 담은 질의문을 자동으로 만듭니다(외부 게시판은 공개될 수 있음).
  - 문의를 등록하면 지점에 중간 안내 문구를 보내고, 같은 쟁점의 새 질의는 진행 중인 문의에 묶습니다(지점 화면에도 표시). 회신을 반영해 승인한 FAQ에는 "외부기관 회신 반영" 표시가 붙습니다.
- F2에서 KB 버전이 바뀌면, 영향받는 FAQ에 **"재검토 필요"** 표시를 붙입니다.

### F4. 평가 하네스 (심사 증거용)
- 테스트셋을 일괄 실행해 판정 일치율, 보류 정확도, 근거 정확도, 처리시간을 산출합니다.
- **A/B 비교 실험**: KB v1(Liner 없음, 보도자료·FAQ만)과 KB v2(Liner로 확보한 후속 문서 반영)를 비교해 L 문항의 정확도 차이를 냅니다.
- 결과는 기획서와 데모 영상에 쓸 표로 출력합니다.

## 6. Liner API 활용 매핑

| 기능 | Liner API | 쓰는 이유 |
|---|---|---|
| F1-1·2 조건 추출, 모듈 분류 | **Router** `liner-gpt-router`(실패 시 Gemini) + `json_schema` strict | 구조화 출력. Claude 라우터는 이 크기의 스키마를 거절(11/13 확인) |
| F1-7 설명 문장 | **Router** `routing_strategy: quality` | 정확한 문장 품질 필요 |
| F2-1 감시 | **Search API**(Web), **MCP `search_legal`** | 공개 웹에서 새 공식 문서 발견. 검증에서 8.28 행정지도를 실제로 발견함 |
| F2-5 조항 구조화 | **Router** `liner-gemini-router`(추론 low, 섹션 병렬) + `json_schema` | 원문을 Fact 후보로 구조화. 약 10초(GPT 16초, Claude 27초 측정) |
| F1·F3 보조 근거 | **Search Agent**(인용 포함 답변) | 지식베이스에 없는 질문의 참고 설명. 원문 대조를 통과해야 표시 |

> 심사 포인트: **"Liner를 빼면 판정이 '보류'에 머문다"**는 것을 A/B 수치로 보여 줍니다(F4).

## 7. 시스템 구성

```
Next.js (App Router, TypeScript) — Vercel 배포
├─ app/                 화면: 창구(채팅+판정 카드) / 정책 감시 / 본점 FAQ / 평가 결과
├─ app/api/judge        F1 판정 (스트리밍 응답)
├─ app/api/watch        F2 감시 실행 + 변경 제안
├─ app/api/faq          F3 질의·승인
├─ lib/liner/           Router·Search·MCP 클라이언트 (재시도, 캐시, 속도 제한 대응)
├─ lib/rules/           규칙 엔진: m1_jeonse_813.ts, m2_renewal_401.ts, dates.ts
├─ lib/verify/          인용 검증기 (설명 문장 ↔ 원문 문장 대조)
├─ data/kb/v1, v2/      facts.json, 원문 조항 청크, 문서 목록
├─ data/bank/           가상 A은행 내부지침 (JSON/MD)
└─ eval/                테스트셋 JSON + 평가 스크립트
```

- **저장소**: 지식베이스는 파일(JSON)로 저장해 버전 관리합니다. FAQ와 승인 기록은 MVP에서 파일·메모리에 두고, 배포 환경에서 필요하면 Vercel KV를 씁니다.
- **검색**: 원문 조항이 수백 개 수준이라 **키워드와 Fact ID 매핑으로 충분**합니다. 벡터 DB는 쓰지 않습니다.
- **키 관리**: `LINER_API_KEY`는 `.env`(로컬)와 Vercel 환경변수에만 둡니다. 저장소에는 `.env.example`만 올립니다.

## 8. 비기능 요구사항
- **안전**
  - 모든 카드에 "본 결과는 공개 규정 기반 참고 정보이며 최종 판단은 여신 승인권자"를 표시합니다.
  - 규제 회피 방법은 안내하지 않습니다.
- **데이터**: 실제 은행명, 고객정보, 내부자료를 쓰지 않습니다. 가상 은행은 "A은행"으로 표기합니다.
- **안정성**
  - Liner 호출에는 재시도와 지수 백오프를 넣고, Search Agent는 순차로 호출합니다(초당 2회 제한).
  - **데모용 결과는 캐시에 저장해 재생**할 수 있게 해 네트워크 장애에 대비합니다.
- **비용**: 크레딧 $200 중 개발과 평가에 $30 이하를 목표로 합니다(검증 단계는 $0.13 사용).
