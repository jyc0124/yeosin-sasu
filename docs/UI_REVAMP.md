# UI 개편 계획 — 창구 직원과 심사위원을 함께 만족시키기

작성 2026-11-22 · 계기: 시중은행 지점 직원 의견 "글이 너무 많고 복잡하다, '역질문'이 생소하다"

## 문제

한 화면에 세 독자의 글이 섞여 있다.

| 독자 | 원하는 것 |
|---|---|
| 창구 직원 | 결론, 할 일, 고객에게 할 말. 빨리 끝내기 |
| 본점 담당 | 질의 처리, 정책 감시 |
| 심사위원 | Liner를 어디에 썼는지, 판정을 코드가 내린다는 것, 근거 추적, 정확도 |

지금은 심사위원용 설명(처리 시간, Liner Router, 근거 번호 F401-01, 근거 자료 v1/v2, 평가 수치)이 창구 화면에 기본으로 펼쳐져 있다.

## 원칙: 지우지 않고 '누가 보느냐'로 나눈다

1. **기본은 창구 화면.** 직원이 보는 화면에는 결론, 할 일, 고객에게 할 말만 둔다.
2. **심사위원 설명은 스위치로 켠다.** 사이드바에 `심사위원 설명 보기` 스위치를 둔다. 제출 링크는 `?view=judge`로 켜진 상태로 연다. 브라우저에 기억하되(localStorage), 저장이 안 되면 꺼진 상태로 동작한다.
3. **켜면 숨긴 것이 다시 보이고, 화면마다 '심사 포인트' 말풍선이 붙는다.** 예: "이 판정은 규칙 엔진(코드)이 내렸습니다. Liner Router는 질문에서 조건만 읽었습니다."
4. **판정 근거는 어느 쪽에서도 지우지 않는다.** 창구 화면에서는 접어 두고, 근거 번호를 누르면 원문이 열린다(근거 추적 원칙 유지).

구현: `ViewMode` 컨텍스트 하나 + `<JudgeOnly>`(심사위원 설명이 켜졌을 때만 보임) + `<JudgeNote>`(심사 포인트 말풍선). 판정 로직은 건드리지 않는다.

## 할 일 (우선순위 순)

### P0. 보기 스위치
- `ViewMode` 컨텍스트, 사이드바 스위치, `?view=judge` 처리.
- 영상·제출 문서의 링크를 `?view=judge`로 바꾼다(docs/PITCH.md, docs/VIDEO.md).

### P1. 판정 화면 (직원이 가장 오래 보는 화면)
| 요소 | 창구 화면 | 심사위원 설명 켬 |
|---|---|---|
| 처리 단계 "조건 읽기 완료 / 항목 5개 · Liner Router · 11.0초" | "이렇게 이해했어요 · 조건 5개 ›" 한 줄(누르면 읽은 조건). 잘못 읽었는지 직원이 확인할 수 있어야 하므로 지우지 않음 | 지금처럼 + 심사 포인트 |
| 오른쪽 근거 패널(원문 전체) | "근거 5건" 제목 목록만, 누르면 원문 | 지금처럼 펼침 |
| 오른쪽 메타(판정 주체, 판정 지식 v2) | 숨김 | 보임 |
| 고객 안내 머리글 "AI 작성, 대조 통과 3문장 · 1.5초" | "고객에게 이렇게 말하세요 [복사]"만 | 보임 |
| 후속 지침 비교(타임머신) | 한 줄 (완료) | 펼친 상태로 시작 |
| 베타 의견 | 한 줄 (완료) | 같음 |

### P1. 첫 화면
- 창구 화면: 질문 입력창을 맨 위로. 예시는 "자주 묻는 상황" 한 줄짜리 목록으로(제목과 결과 배지만).
- 심사위원 설명 켬: 지금의 기능 소개 카드 3개, 대출 규모 통계, "왜 막히나" 태그, "표현을 바꾼 질문 28개 모두 정답" 문구.

### P2. 사이드바와 용어
- '판정 근거 자료 v2' 상자 → 창구 화면에서는 "최신 지침 반영 · 11.13 기준" 한 줄. 버전 이름(v1/v2)은 심사위원 설명에서만.
- '평가 결과' 메뉴 → 심사위원 설명을 켰을 때만.
- 근거 조항 코드(F401-01, 401본 2-(1)) → 창구 화면에서는 문서 이름만("8.13 보도자료 FAQ").
- 'Liner Router', '규칙 엔진' 같은 구현 이름 → 창구 화면에서는 숨김.

### P3. 내 질의 · 본점 · 정책 감시
- 빈 상태 설명 문단(3~4줄)을 한 줄 + 예시 버튼으로 줄인다. 긴 설명은 심사위원 설명으로.

## 검증
- **글자 수**: 같은 7개 대표 사례로 판정 화면에 보이는 글자 수를 개편 전후로 잰다(창구 화면 기준, 목표 절반 이하).
- **기능 회귀**: `npm test`, `npm run build`, 대표 사례 7개 화면 캡처(두 모드).
- **현장 확인**: 의견을 준 지점 직원에게 창구 화면을 다시 보여 준다. 질문은 "어디가 아직 복잡한가요?" 하나.
- **심사위원 관점**: `?view=judge` 링크만 받은 사람이 Liner 역할, 코드 판정, 근거 추적, 정확도 수치를 3분 안에 찾는지 확인한다.

## 하지 않는 것
- 판정 로직, 근거 데이터, 고객 안내 문장 검증 규칙은 바꾸지 않는다.
- 직원 화면이라도 근거를 지우지 않는다(접기만).
- 역할별 로그인은 만들지 않는다(시제품 범위 밖).

## 진행 상황 (2026-11-22)
- **P0 완료**: `app/_components/viewStore.tsx`(ViewMode, `JudgeOnly`, `JudgeNote`, `ViewSwitch`), 사이드바 스위치(좁은 화면은 위쪽 막대), `?view=judge|branch`. README·PROPOSAL 링크를 `?view=judge`로.
- **P1 완료**: 판정 화면(처리 단계 한 줄 "이렇게 이해했어요 · 조건 N개", 판정 단계·추출 경고·메타·고객 안내 처리 정보는 심사위원 설명에서만, 근거 패널은 접고 번호를 누르면 열림, 심사위원 설명에서는 '왜 이렇게 판단했나요?'·전후 비교가 펼친 채 시작) · 첫 화면(창구: 입력창 위로, '자주 묻는 상황' 제목+배지+질문 한 줄).
- **P2 일부**: 사이드바 근거 자료 상자(창구: "최신 정부 지침 반영"), '평가 결과' 메뉴는 심사위원 설명에서만.
- 남은 것: P2 근거 조항 코드 표기, P3 내 질의·본점·정책 감시 설명 줄이기, 글자 수 전후 측정.
- **제출 문서 용어 완료**: VIDEO·PITCH·PROPOSAL·README의 판정 이름을 화면 표기로, 영상은 `?view=judge`로 녹화하고 스위치 시연 한 번.

## 이미 끝난 것 (2026-11-22)
- 판정 이름을 창구 말로 바꿈(가능, 조건 충족 시 가능, 불가, 고객 확인 필요, 본점 문의, 심사위 상정, 은행 지침 확인).
- 판정 카드: 결론 → 고객에게 물어보세요(답 버튼) → 할 일 체크리스트 → 주의 → 접힌 '왜 이렇게 판단했나요?'.
- 고객 안내 복사 버튼, 후속 지침 비교 한 줄로 접기, 베타 의견 한 줄로 줄이기.

## 응답 속도 (2026-11-22)
- 실측: 판정 10~11초가 거의 전부 조건 추출(Liner Router 1회). 스트리밍으로 받아 보면 첫 글자 약 2초, 이후는 JSON 약 2,500자 생성(실제 값은 500~700자, 나머지 null·공백).
- 적용 1 — 한 줄 JSON 지시(`lib/extract/prompt.ts` '출력 형식'): 추출 평가 중앙값 10.4초 → 7.7초(45문항), 10.0초 → 7.4초(표현 바꾼 28문항). 판정 정확도 28/28, 45문항 중 44/45.
  - 틀린 1건 B09("3월에 연장해 준다고 문자 보낸 적 있대요" → 통보 기록을 none으로 읽어 조건부→불허, 엄격한 방향)는 **변경 전 지시로도 캐시 없이 4회 중 3회 같은 결과**(기존 흔들림, 아침 45/45는 저장된 1회 결과). 새 지시는 4회 모두 같음. 고객 진술만 있는 통보를 record/none 중 무엇으로 볼지는 별도 쟁점으로 남긴다(특정 문항 맞추기 수정 금지).
  - `reasoning_effort: low`는 평균 −1.5초에 5문항 중 1문항 결과가 달라져 쓰지 않음.
- 적용 2 — 스트리밍 표시: `lib/liner/router.ts` `onDelta`(스트리밍 실패 시 일반 호출, 시간 초과는 재시도 안 함, 캐시 키 동일) → `lib/extract/partial.ts`(끝나지 않은 JSON에서 확실한 부분만) → `/api/judge` `partial` 이벤트(0.3초 간격) → 화면 '지금까지 읽은 내용' 칩. 판정은 기존대로 추출이 끝난 뒤 코드가 낸다.
- 적용 3 — 기다림 화면: 경과 초·"보통 10초 안팎"·결과 모양 뼈대.
