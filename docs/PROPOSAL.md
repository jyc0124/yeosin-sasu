# 여신 사수 — 규정 막힐 때 바로 묻는 대출 규제 사수

> 은행 지점 창구 직원을 위한 대출 규제 판정 에이전트 · 장재영 1인 참가작 · https://loandesk-copilot-rosy.vercel.app/?view=judge
> 다루는 정책: **2026.8.13 비거주 1주택자 전세대출 제한**, **2026.4.1 다주택자 주담대 만기연장 제한**
> 이 문서는 기획서 **상세판**입니다. 제출용 2쪽 기획서는 [`docs/submission/여신사수_기획서.pdf`](submission/여신사수_기획서.pdf)(원본 `docs/submission/proposal.html`)이며, 숫자와 내용은 같습니다.

**좋은 사수는 아는 건 근거와 함께 바로 알려 주고, 모르는 건 "이건 본점에 물어보자"고 합니다.** 여신 사수는 판정을 LLM이 아니라 규칙 엔진(코드)이 내리고, 정부 발표 자료에 답이 없으면 확답하지 않고 본점으로 올립니다.

## 0. 만든 이유: 지점 직원의 고충, 그리고 Liner가 가장 잘하는 일

시중은행 지점 직원 커뮤니티에서 들은 고충에서 시작했습니다. 정부 대책은 계속 바뀌는데 세부 지침은 늦게 내려와, 직원들은 건마다 규정을 찾고 본점 회신을 기다리느라 퇴근이 늦어지고, 급한 고객 앞에서 제때 답하지 못하는 스트레스를 털어놓고 있었습니다.

이 문제의 답은 **최신 공식 문서를 찾아 출처를 붙이되, 틀리게 단정하지 않는 것**입니다. 이것은 Liner가 가장 잘하는 일 — 출처가 붙는 검색, 여러 문서를 찾아 읽는 조사, 업무 흐름에 넣을 수 있는 API — 과 겹칩니다. 그래서 **처음부터 Liner의 강점이 가장 값진 곳**, 출처와 최신성이 중요하고 오답 비용이 큰 금융 창구를 골랐습니다. 개발 첫날(11/13, $0.13) 실험으로 강점과 약점을 직접 재고, 찾기·읽기는 Liner에, 결론은 코드에 맡겼습니다(§4).

| Liner가 잘하는 일 | 이 문제에서 잰 값 |
|---|---|
| 출처가 붙는 검색 | 인용 18/18 원문 대조 · 모든 근거에 문장 번호(Fact ID) |
| 여러 문서를 찾아 읽는 조사 | 보도자료 뒤 8.28 행정지도 발견 · 현장 쟁점 9개 공식 출처 193건 |
| 법령 검색(MCP) | 정책 감시에 `search_legal` |
| 업무에 넣는 API | 감시·질의서·쟁점 대장 안에서 동작 · 판정 1건 $0.026 |
| (약점) 단정 | 첫날 실험으로 측정 → 결론은 규칙 엔진(코드)이 내림 |

**모두에게 이득이 되도록 만들었습니다.**
- **지점 직원**: 근거가 붙은 답을 창구에서 바로 받고, 본점 회신을 기다리는 일이 줄어듭니다.
- **Liner**: 출처가 곧 가치인 금융 업무 안에서 API가 매일 쓰이는 사례가 됩니다(정책 감시·판정 1건 $0.026).
- **만든 사람**: 은행마다 구축(내규 반영) + 규제 감시 구독으로 사업이 됩니다.

**만든 사람.** 저는 은행원이 아닙니다. 컨설팅, AI 교육, AI로 제품·서비스를 만들어 사업화하는 일을 하며 여러 조직의 현장 고충을 듣고 AI로 풀어 왔습니다. 지점 직원 커뮤니티에서 같은 질문이 반복되는 것을 보고, 혼자 판단하지 않고 현직 직원에게 네 번 검증받으며 만들었습니다(설계 · 11.21 현장 질문 · 11.22 사용 검토 · 11.24 재확인).

## 1. 문제: 창구는 "어느 규정이 이 고객에게 언제 기준으로 적용되나"에서 막힌다

- 고객은 "이 대출 연장 되나요?"라고 바로 묻습니다. 하지만 규정은 보도자료 → FAQ → 행정지도로 계속 덧붙고, **경과조치·증액 조건 같은 결정적 내용이 보도자료·FAQ에는 없고 행정지도에만** 있습니다(8.28 행정지도).
- 지점 직원 커뮤니티에서 같은 유형의 해석 질문이 반복되고, 답이 공식 근거인지 개인 경험인지 구분되지 않습니다.
- 현직 지점 직원(1명)에 따르면 규정 해석 질문 하나에 **수 분~30분**이 걸리고, 가장 오래 걸리는 건 본점이 **외부기관(HUG·국토부 등) 문의 게시판에 글을 올리고 회신을 기다릴 때**로 **2~3일**이 걸리기도 합니다.
- 창구에서는 문서 이름을 모른 채 고객 상황만 묻습니다. 웹 검색을 켠 ChatGPT에 고객 질문 6개를 넣자 **8.28 행정지도를 한 번도 인용하지 못했고**, 대출 증액 연장을 "종전 규정"이라고 답했습니다(11/22, §4).
- ChatGPT(추론 High, 스스로 웹 검색)에 같은 질문 10개를 넣자 FAQ 수준 질문은 맞혔지만, **행정지도를 몰라 틀리고(B02·C07), 자료에 없는 것을 단정하고(C02), 지점이 답하면 안 되는 것에 "네"라고 하고, 만기를 앞당겨 규제를 피하는 방법까지 제안**했습니다. 창구에서는 이런 오답이 민원·사고로 이어집니다.
- 영향 규모: 8.13 영향권 전세대출 약 6만 건, 4.1 대상 주담대 중 올해 만기 도래 약 1.2만 건(금융위 8.13 대책 본문).

## 2. 해결: 판정은 코드가, 말은 Liner가, 모르는 건 본점으로

| 지점 직원이 하던 일 | 여신 사수 |
|---|---|
| 보도자료·FAQ·행정지도를 찾아 대조 | 고객 말 그대로 입력 → **규칙 엔진이 판정**(가능·조건 충족 시 가능·불가·고객 확인 필요·심사위 상정·본점 문의·은행 지침 확인·안내 8종), 모든 근거에 정부 발표 자료 문장(Fact ID)과 원본 링크 |
| 빠진 사실을 몰라 잘못 답함 | 결론이 갈리는 사실이 없으면 **고객에게 물어볼 것**을 항목별로 제시(선택지·미확인, 사실이 여럿이면 칸을 나눔) → 한 번에 답하고 다시 판정 → **바뀐 조건과 바뀐 결론**(예: 불가 → 가능)을 카드 위에 표시. 잘못 읽힌 조건은 그 항목만 고쳐 다시 판정 |
| 본점 질의서 작성·회신 대기 | 판정 카드로 **질의서 자동 작성**, 본점 회신은 사례 FAQ로 등록돼 같은 쟁점에 자동 표시 |
| 여신심사위 상정·일정 확인 | 본점이 상정을 결정하면 지점은 서류 체크만, 안건 등록·개최일 계산·결과 통보는 에이전트 |
| 정부 후속 지침 확인 | 본점의 **정책 감시**가 Liner로 후속 문서를 찾아 원본 대조·승인 후 판정 기준에 반영(시제품은 원본을 등록하고 규칙으로 옮겨 둔 8.28 행정지도로 같은 브라우저에서 시연. 운영에서는 새 문서마다 ① 원본 등록 ② 조항을 Fact로 정리 ③ 규칙 반영 ④ 테스트 재검증 ⑤ 담당자 승인 후 서버에서 전 지점 적용 — 감시가 찾은 문서가 자동으로 규칙이 되지는 않음) |
| 보증기관(HUG·HF) 기준 따로 찾기 | 판정과 별개로 **보증기관 공식 문서 원문**(HF 전세자금보증 업무지침 등)을 기준일·링크와 함께 판정 카드 옆에 연결, 개정 여부는 정책 감시가 확인 |

안전장치: 규칙에 없는 사실(분양권·입주권 등)이 있으면 확정 판정을 **본점 문의**로 바꿉니다. 규제 회피 방법은 안내하지 않고, 고객 안내 문장은 정부 발표 자료와 대조를 통과한 것만 냅니다. 질문에 주민번호·전화번호가 보이면 외부로 보내지 않습니다.

## 3. 완성도: 틀리면 안 되는 곳에서 안 틀리게 설계했다

| 평가 | 결과 |
|---|---|
| 테스트 질문 45문항(실무 쟁점 기반, 개발에 사용, 정답 고정. 현직자가 15문항의 현실성을 평가해 모두 5점 중 4점) | **45/45**, 위험 오류 **0** |
| 표현만 바꾼 질문 28개(개발에 쓰지 않음) | **28/28** |
| 처음 보는 새 상황 질문 41개(21개는 첫 측정(16/21) 뒤 일반 규칙을 고쳤고, 20개는 고치기 전에 떼어 둔 검증용) | **41/41, 틀린 확답 0** |
| 비교: LLM 단독 / LLM + 정부 발표 자료 전체 | 24.4% / 71.1% (45문항) |
| 외부 출제 50문항(Codex가 독립 출제·채점, 어려운 질문) | Codex 채점 '판정이 원문상 정당' 36/50(72%, 고치기 전; 판정 코드 일치는 33/50), 위험 오류 2 → 일반 규칙으로 고친 뒤 판정만 다시 돌려 **0** |
| 비교: ChatGPT 일반 채팅(추론 High, 자동 웹 검색) | 10문항 중 정답 5 · 부분 3 · 오답 2 ↔ 여신 사수 10/10 |

- 추출된 조건이 같으면 판정은 항상 같습니다(규칙 엔진). 자동 테스트 523개. 평가는 세트당 1회 실행, 정답은 직접 정했습니다.
- 지점·본점 역할별 화면, 판정 카드의 정부 규정과 은행 지침 구분 표시, 해석 쟁점 대장(쟁점이 생기고 → 회신되고 → 정부 기준으로 닫히는 흐름)까지 실제 업무 흐름으로 동작합니다.
- **지점 직원 커뮤니티의 현장 질문으로 만들고, 고치고, 검토받았습니다.** 한 사람의 의견이 아니라 커뮤니티에서 여러 직원이 실제로 묻고 답한 질문을 세 번 반영했습니다: ① 설계 때 반복되는 쟁점 유형을 다시 쓴 테스트 질문 15개(45개 중) ② 11/21 커뮤니티에서 실제로 오간 질문을 현직자가 일반화해 추린 현장 질문 10개 주제·14문항 → 고치기 전 범위 안 9개 중 정답 2, 고친 뒤 **14문항 모두 묻는 말에 직접 답함**(직접 채점, 현직자 정답 검수 전) ③ 11/22 현직 직원이 커뮤니티의 실제 질문을 직접 넣어 보고 커뮤니티의 실제 답과 비교(아래).
- **현직 시중은행 지점 직원 검토(11/22, 커뮤니티 소속 1명이 직접 사용)**: 이전에 막혔던 질문(같은 등본의 자녀·손자 주택 합산)은 **개선 확인**, 직원 커뮤니티의 실제 답변과 핵심이 일치. 커뮤니티의 실제 질문 3건은 **핵심 결론을 확답하지 못했고**, 직원은 조건 부족·기관별 기준이 섞여 있어 오답률로 계산하지 않았습니다. 총평: "정부 정책은 잘 설명하는 편이지만, 보증기관과 은행별 정보가 부족해 심도 있는 실무 답변까지는 어려워 보입니다."
- 검토 지적을 바로 반영(11/23, 판정 결과 변화 없음 — 저장 평가 재판정으로 확인): 화면에 내부 항목명 노출 제거 · 무주택 고객 질문에 1주택자 기준을 답처럼 내던 경로 차단 · 담보 지역을 모르는 '불가'에 결론의 전제 표시 · **고객 확인 질문에 항목별로 한 번에 답하고, 잘못 답한 조건만 고쳐 다시 판정** · 결과를 '확인된 내용 / 고객 확인 / 본점·기관 확인'으로 분리 · **보증기관 공식 문서 연결**(아래 §4). 후속 질문이 묻지 않은 쪽으로 넘어가는 문제는 아직 남아 있습니다.
- **제출 전 Codex(AI) 독립 검토(11/23, 2회)**: Codex가 독립적으로 찾은 드문 판정 경로를 규칙 엔진에 직접 넣어 하나씩 재현한 뒤, 안 되는 대출이 '가능'으로 나올 수 있던 11곳을 일반 규칙으로 막았습니다(예: 다주택자의 법적 의무 예외, 연장 전용 예외의 신규 적용, 모르는 날짜·소재지가 한도·DSR 결론을 뒤집는 경우, 달만 아는 날짜가 4.16 경계에 걸리는 경우, 법인 HOMS 조회 불가인데 이미 다주택으로 확인된 경우). 저장된 평가 3,497건을 판정만 다시 돌려 확인했습니다(Liner $0): 테스트 45·외부 출제·현장·처음 보는 질문의 판정은 그대로입니다. 바뀐 것은 개발용 질문 3개뿐입니다. 1개는 정답 쪽으로 바뀌었고, 2개는 '가능'에서 '고객 확인 필요'와 '불가'로, 덜 위험한 쪽으로 바뀌었습니다. '불가'가 된 1개는 조건 추출이 주택 수를 잘못 읽은 문항이라 오답입니다.
- **되묻고 → 답을 받아 → 다시 판정하는 흐름을 끝까지 점검(11/23)**: 규칙 엔진이 고객에게 묻는 질문 58종을 모두 확인해, 한 질문에 사실이 여럿이면(예: 담보 소재지와 아파트 여부) 칸을 나눴습니다. 나눈 칸의 답이 조건으로 제대로 읽히는지 실제 Liner 호출로 확인했습니다(10칸짜리 사례 포함). 그 과정에서 찾은 문제 3가지도 고쳤습니다: ① 답하지 않은 조건(담보 지역)이 결론을 바꿀 수 있는데 '가능'을 내던 경로 → 먼저 되묻기 ② 예외 사유를 모두 "없음"으로 답해도 읽히지 않던 문제 → 조건으로 반영 ③ 기준을 묻는 질문은 답을 다 해도 '본점 문의'에 머물던 문제 → 답한 조건으로 판정. 저장 평가 재판정 결과, 의도한 1건(지역 모르면 되묻기) 외에 판정 변화가 없습니다.

## 4. Liner API: 에이전트의 앞·뒤·바깥을 맡는다

**고객 상황만으로 8.28 행정지도를 찾은 건 Liner였고, 그걸 API로 매일 돌릴 수 있습니다.** 창구는 문서 이름을 모르고 고객 상황만 압니다. 같은 창구 질문으로 Liner Search Agent는 행정지도를 찾았고(1/3) ChatGPT 웹 검색·일반 웹 검색은 못 찾았습니다(0/3 · 0/3, `data/compare/search_1122/RESULT.md`). 개발 첫날 이렇게 찾은 문서 한 건이 정답률 33% → 100%의 열쇠였습니다. 문서 이름을 알면 ChatGPT도 찾습니다. 차이는 처음 찾는 힘과, 그걸 API로 매일 자동 감시할 수 있다는 데(검색 1,000회 $1) 있습니다.

**Liner와 함께 자란 과정** (화면: `/story` 「Liner와 만든 이야기」): **11/13 첫 실험($0.13)에서 보도자료에 없던 8.28 행정지도 발견** → 문서 한 건으로 최신 정보 질문 **33% → 100%** → 정책 감시(**API라 매일 돌릴 수 있는 구조**, 지금은 본점 담당자가 버튼으로 실행) → 현장 질문·검토를 받을 때마다 Liner로 근거를 넓힘(쟁점 9개 공식 출처 193건, 보증기관 문서 8건) → **고객 상황만 말해도 그 조항으로 답함**(ChatGPT 웹 검색 0/6 ↔ 5/6).

**Liner가 찾은 8.28 행정지도 한 건으로 정답이 된 문항: 모두 15개.** 같은 문서로 정답이 된 문항은 테스트 질문 4개 외에 다른 세트에서도 11개(외부 출제 6·표현 바꾼 3·새 상황 1·현장 1, 그중 3개는 v1이면 위험 오류) — 저장된 조건 추출에 근거 자료만 바꿔 다시 판정한 결과(11/23, Liner $0).

**Liner를 먼저 시험하고, 특성에 맞춰 역할을 나눴습니다.** 개발 첫날(11/13) $0.13으로 Liner 검색과 Search Agent를 시험해 강점과 한계를 측정했고(`data/liner_spike/REPORT.md`), 그 결과로 설계를 정했습니다. 한 줄로: **Liner는 찾기와 읽기에 강하고 단정하기에는 약하다 → 찾기·읽기는 Liner에, 결론은 코드에.**

**Liner가 만든 차이: 창구 직원은 고객 상황만 묻는다**
- 사람들은 ChatGPT에 "8.28 행정지도를 찾아 답해 줘"라고 묻지 않습니다. 고객 상황만 말합니다. 같은 고객 질문 6개(현장 질문 3 + 창구 질문 3)를 넣었더니(11/22, 각 1회, 정답 기준 8.28 행정지도 원문):
  - **ChatGPT(웹 검색 켬·추론 High): 맞음 2 · 부분 3 · 위험 오답 1, 8.28 행정지도 인용 0/6.** 위험 오답은 "12월에 대출금을 증액해 연장해도 종전 규정"(원문: 증액하면 변경 규정). "기준일이 언제냐"에는 "공식 자료로 확정할 수 없다"(원문: 만기도래일).
  - **여신 사수: 맞음 5 · 되물음 1 · 위험 0, 8.28 행정지도 근거 5/6.** 되물은 1건(종전 한도 유지 조건을 물었는데 기준 대신 주택 수를 먼저 확인)은 그대로 밝힙니다.
- 문서 이름을 넣으면 ChatGPT도 이 문서를 찾습니다(3/3). 차이는 **고객 질문만으로 찾느냐**입니다. 이번 비교에서 고객 질문만으로 이 문서를 찾은 것은 Liner Search Agent뿐이었고, 최초 발견(11/13)도 질문으로 물어 찾았습니다. 여신 사수는 Liner가 찾아온 문서를 원문 대조·승인해 규칙으로 넣어 두므로, **고객 상황만 물어도 그 조항으로 답합니다.**

**왜 Liner였나**
- **보도자료 뒤의 문서를 찾아온다**: 같은 검색어 6개로 8.28 행정지도 원문 찾기 — **Liner 3/6, ChatGPT(웹 검색 켬) 3/6, 일반 웹 검색 0/6**(11/22, `data/compare/search_1122/`). 문서 이름 검색은 비슷하지만(ChatGPT 3/3·Liner 2/3) **고객 상황(창구 질문)만으로 찾은 건 Liner(1/3, ChatGPT·웹 0/3)**였고, **찾은 뒤 LLM 요약은 ChatGPT·Liner Search Agent 모두 경과조치를 거꾸로 읽음** → 여신 사수는 원문을 대조·승인한 조항으로 규칙 엔진이 판정. Liner는 이 검색을 API로 반복 실행(정책 감시, 버튼 한 번).
- **검색 가격(1,000회)**: Liner $1 · Brave $5 · Perplexity Search $5 · Tavily 약 $8 · OpenAI 웹 검색 도구 $10+토큰(각 사 공개 가격, 11/22 확인).
- **출처가 붙어 와서 검증할 수 있다**: 인용 18/18 원본 일치, 출처 신뢰도로 공식 출처만 남김.
- **키 하나로 모델·검색·법령 도구**: GPT·Gemini 라우팅, 웹 검색, 법령 검색(search_legal)을 같은 키·크레딧으로. 한 모델이 실패하면 다른 모델로.
- **비용이 싸고 실시간으로 보인다**: credits API로 잔액·사용액을 바로 조회해 평가마다 상한을 정해 그 안에서 실행(외부 출제 50문항 측정: 상한 $5, 실제 $3.22). 판정 1,000건 ≈ $26(실측 단가로 계산).

- Liner Search Agent 답변은 실행마다 달라 판정 경로에 넣지 않았습니다. Liner가 찾아온 것은 **정부 발표 자료와 대조하고 사람이 승인한 뒤에만** 판정에 들어갑니다.
- 창구 판정 1건 Liner 비용: **약 $0.026**(11/22 실측). 개발·평가·시연 전체 사용액 $123.53(6,264회, 11/22 기준, 대부분 처음 보는 질문 반복 평가, 제출 직전 재조회).

## 5. 다른 조직·직무로 확장

**공개 자료만으로 여기까지 왔습니다. 내부 자료가 들어오면 같은 길로 넓힙니다.** 지금 막히는 질문은 대부분 공개되지 않은 은행 내규와 보증기관 심사 기준에서 나옵니다(11/22 현직자 검토). 그 자료가 들어갈 자리는 이미 만들어 두었습니다.
- **문서가 들어가면 실제로 좋아진다**: Liner가 찾은 문서 한 건(8.28 행정지도)을 넣자 최신 정보가 필요한 질문이 33% → 100%가 됐습니다. 엔진은 그대로이고 문서만 달라졌습니다. 은행 내규와 보증기관 지침은 이런 문서가 수십 건 더 있는 것입니다.
- **은행 내규 자리**: 가상 A은행 지침을 별도 파일로 분리했고, 화면은 이미 정부 규정과 은행 지침을 나눠 표시합니다. 다만 일부 은행 기준 수치·문구는 규칙 코드에도 있어, 실제 은행 내규를 넣으려면 공통 규칙은 그대로 두고 그 은행 기준을 규칙에 더한 뒤 다시 검증해야 합니다.
- **보증기관 지침 자리**: 현직자 검토 다음 날 HF 전세자금보증 업무지침 등 공식 문서 8건을 찾아(Liner 검색 18회 $0.018 + 공식 사이트 직접 확인) 원문 대조 테스트와 개정 감시까지 붙여 창구에 연결했습니다. 지금 판정에 넣지 않은 것은 공개된 원문이 요약본·상품 안내뿐이기 때문입니다. 지침 전문이 있으면 정부 규제와 같은 방식으로 판정에 넣습니다.
- **같은 방식**: Liner로 찾고 개정을 감시 → 원문과 대조 → 사실 목록(Fact ID) + 규칙 모듈 → 담당자 승인 후 반영. 8.28 행정지도는 이 흐름을 판정 반영까지 끝까지 돌려 봤고, 보증기관 자료는 찾아서 원문과 대조해 화면에 연결하는 단계까지 했습니다(보증기관 기준은 판정하지 않음, SGI 문서는 미확보).

**여러 은행으로, 사업으로.** 은행마다 새로 만들 필요가 없는 구조라, 한 번 만든 것을 여러 은행이 함께 씁니다.
- **다른 직무 — 이미 본점까지 넓힘**: 같은 구조(Liner가 찾고 → 사람이 확인하고 → 코드가 판정)를 지점 창구 직원에서 **본점 여신 담당** 직무로 넓혀 만들었습니다. 지점이 확답하면 안 되는 건 질의서를 자동으로 쓰고, 본점은 외부기관에 묻기 전에 Liner로 공식 출처를 조사하며, 회신은 해석 쟁점 대장과 사례 FAQ로 전 지점에 돌아가고, 여신심사위 안건 등록·개최일 계산·결과 통보까지 처리합니다. 그다음 직무 후보는 규정이 자주 바뀌고 근거가 필요한 보험 인수심사·카드 심사·공공기관 민원 창구입니다(아직 시험하지 않은 가능성).
- **넓히는 순서**: ① 1금융권 시중은행(첫 대상) → ② 2금융권(상호금융·저축은행·보험사 등의 가계대출 창구) → ③ 규정 판단이 많은 다른 창구(보험 인수심사·카드 심사·공공기관 민원 등, 아직 시험하지 않은 가능성). ②가 바로 다음인 이유: 같은 규제가 금융권 전체에 걸립니다. 유주택자 전세대출 한도 2억원은 전 금융권 가계 차주 대상(F828-09), DSR은 은행권 40%·2금융권 50%(F813-12·F828-11), 다주택자 만기연장 제한도 각 업권 감독규정의 세대 기준(F401-01). 엔진은 이미 업권별 DSR 기준을 나눠 판정합니다. 2금융권 규모: 저축은행 79곳(점포 약 260, 저축은행중앙회 2025.1)·농·축협 1,110곳(지점 3,705, 농협 2025.12)·신협 862곳(점포 1,702, 신협중앙회 2025)·새마을금고 1,251곳(행안부 '25.12말)으로 기관만 3,300곳이 넘고(수협·산림조합 제외), 상호금융조합 총여신 540.2조원(금감원 「2025년 저축은행 및 상호금융조합 영업실적」). 2금융권 주택담보대출 잔액 161조원(전체의 14.5%, 보험연구원 「업권별 주택담보대출 리스크 분석」 2025.1, '24.3분기 기준) → 4.1 다주택자 주담대 만기연장 판정을 그대로 쓸 수 있음. 2금융권 첫 대상은 조합이 3,200곳 넘는(농·축협·신협·새마을금고) 상호금융으로 봄(고객 인터뷰·구매 의사 검증 전 가설). 업권별 전세대출 비중은 공식 통계를 찾지 못해 쓰지 않음. 조사: Liner Search API 10회 + 5회(`scripts/research/market2-1123.ts`·`market3-1124.ts`, `data/research_market/search2_1123.json`·`search3_1124.json`).
- **시장(공식 통계·통계 인용 보도)**: 전국 은행 점포 **5,523곳**('25.9월말, 금융위 「은행 점포폐쇄 대응방안」 2026.2)이 같은 규제를 같은 날부터 적용해야 합니다. 가계대출 잔액 **1,891.3조원**(2026 2분기말, 한국은행 가계신용), 그중 예금은행 전세대출 **165.7조원**(2026 1분기말, 한국은행 통계 보도 인용). 8.13 규제 영향권만 전세대출 약 6만 건(9.3조원), 4.1 대책 대상 주담대 중 2026년 만기 도래 약 1.2만 건입니다(금융위 8.13 대책).
- **규제가 자주 바뀐다**: 약 14개월 사이 대출 대책 4번(2025.6.27 전세대출 보증비율 90→80% · 2025.9.7 · 2026.4.1 · 2026.8.13)과 후속 행정지도(8.28)가 나왔습니다. 바뀔 때마다 모든 점포가 다시 배워야 하는 일을, 한 번 반영해 모든 점포에 적용합니다.
- **은행이 AI를 못 쓰는 이유를 설계로 푼다**: 금융위는 금융권 AI 활용의 장애로 망분리, 금융 특화 데이터 부족, **환각(hallucination) 같은 불확실성**을 꼽았습니다(「금융권 생성형 AI 활용 지원방안」 2024.12). 여신 사수는 결론을 LLM이 아니라 코드가 내리고 모든 근거를 정부 발표 자료 번호로 추적해 환각 위험을 구조로 줄입니다. 상용 AI는 망분리 규제 샌드박스로 허용을 넓히는 방향이라, 은행 도입 경로도 열려 있습니다.
- **공통은 한 번만**: 판정 결론은 정부 규제라 모든 은행에 같습니다. 보증기관(HF·HUG·SGI) 기준도 은행과 상관없이 같습니다. 은행마다 다른 것은 내규·심사 기준 파일뿐이고, 이미 따로 분리되어 있습니다.
- **은행이 사는 이유는 사고 위험**: 잘못된 안내는 민원과 손실로 이어집니다. 여신 사수는 위험 오류(안 되는 대출을 된다고 안내) 0건, 규제 회피 비안내, 모든 판정의 근거 번호 추적으로 이 위험을 줄이고, 감사 대응 기록도 남깁니다. (시간 단축 효과는 재지 않았습니다.)
- **운영비가 싸다**: 판정 1건 약 $0.026(실측), 1,000건 약 $26. 정책 감시 1회 약 $0.008. 은행이 늘어도 비용은 사용량만큼만 늘어납니다.
- **수익 모델(가정)**: 은행별 구축(내규·심사 기준 반영) + 규제 감시·기준 갱신 구독. 새 규제가 나올 때마다 한 번 반영하면 모든 고객 은행에 함께 적용됩니다.
- **Liner에게도**: 은행 하나가 늘 때마다 매일 정책 감시와 창구 판정이 Liner API 사용량이 됩니다. 금융처럼 규제가 자주 바뀌는 업종에서 Liner 검색이 업무 시스템 안에서 매일 쓰이는 사례입니다.

- **은행별 지침 교체**: 결론은 정부 규정(모든 은행 공통), 서류·기간·절차는 은행 지침 파일(`data/bank/`)에서 옵니다. 은행마다 다른 기준은 이 파일로 분리했고, 실제 은행 내규를 넣을 때는 규칙 코드에 남은 일부 수치·문구를 그 은행 기준으로 맞추고 같은 평가로 다시 검증합니다. 화면에서도 '은행 지침' 표시로 둘을 구분합니다.
- **다른 정책으로**: 정책은 사실 목록(Fact ID)과 규칙 모듈 단위로 추가합니다. 같은 구조로 DSR·생애최초·정책대출 등으로 넓힐 수 있습니다.
- **스스로 좋아지는 구조**: 정책 감시(후속 문서) + 해석 쟁점 대장(본점 해석 → 사례 FAQ) → 지점 판정이 계속 갱신됩니다.
- **정부 규제 × 기관 기준**: 판정은 정부 규제로, 보증기관 기준은 공식 원문 연결로 나눠 둡니다. 기관 문서가 개정되면 정책 감시가 알리고 본점이 발췌·기준일을 갱신합니다. 기관 기준까지 판정하려면 같은 방식(사실 목록 + 규칙 모듈)으로 기관별 모듈을 추가합니다.
- **창구 서류 업무까지(현장 피드백 11/23)**: 창구는 고객이 준 주소로 등기부등본을 떼고, 소득 서류를 스캔해 등록하는 흐름에 익숙합니다. 이 흐름이 들어갈 자리는 이미 있습니다. 조건(사실)과 판정(코드)이 나뉘어 있어 서류에서 읽은 값도 같은 조건 칸에 들어가고, '조건 수정' 화면이 그 값을 확인·수정하는 자리입니다. 단계: ① 가상 서류로 조건 채우기(등기부등본 → 소재지·아파트 여부·소유자·지분, 소득 서류 → 소득) → ② 은행 내부망의 등기 조회·주택소유확인·서류 스캔 시스템과 연결. 원칙은 그대로, 서류에서 읽은 값도 직원이 확인한 뒤에만 판정에 씁니다. 지금 구현하지 않은 이유: 등기부 발급은 공개 API가 없고(유료 대행·수수료), 실제 주소·서류는 실제 개인정보이며, 결론을 가르는 세대 전체 주택 수는 등기부 한 장으로 알 수 없습니다.
- **운영 전환에 필요한 것**: 질의·FAQ를 서버 저장소로(지금은 시연용 브라우저 저장), 정책 감시 정기 실행, 은행 내부망 배포와 망분리 대응(외부 API는 규제 샌드박스 등 은행 보안 절차를 거쳐야 함).

## 7. 한계 (그대로 밝힘)

평가 문항은 직접 만들었고, 표의 값은 세트별 최종 보고 실행 1회입니다. 모든 코드와 데이터는 해커톤 기간(2026.11.13 첫 커밋 ~ 제출)에 새로 만들었고, 가져다 쓴 것은 공개 라이브러리와 공개 자료(정부 발표 자료, HF·HUG 공개 문서)뿐입니다(자세한 구분은 README). 장재영 1인이 대회에 참가해 기획·조사·개발·평가·영상까지 모두 직접 했고, AI 도구(Claude Code·Codex)를 썼습니다. 현직 지점 직원은 써 보고 의견만 주었습니다. 현직자 검토는 1명이 고른 사례에 대한 의견이며 전체 정확도 평가가 아닙니다. 보증기관(HUG·HF·SGI) 기준은 판정하지 않고 공개 원문만 연결하며, SGI는 공식 기준 문서를 확보하지 못했습니다(상품공시가 보안 프로그램 설치를 요구). 은행 지침은 가상 A은행 기준이며 실제 은행 기준이 아닙니다. 시간 단축 효과는 측정하지 않았습니다. 판정 보조 도구이며, 최종 판단은 금융회사의 기준과 여신심사 절차를 따릅니다.
